You own one terminal MID-tier **WordPress/PHP implementation** phase in the current session. WordPress is a primary production path. `$@` must identify exactly one approved, implementation-grade plan; MID-tier ownership expresses configured implementation intent and does not change the active model.

Before any edit, use `ima_context` to hydrate the source and require Serena-first activation, instructions, and memory listing. Inspect planned project files/symbols narrowly. Load relevant WordPress/PHP skills before editing, including `php-fp-wordpress` where available and applicable environment/domain skills such as `phpunit-wp`, `wp-ddev`, `wp-local`, `ima-forms-expert`, `ima-bootstrap`, `jquery`, `js-fp-wordpress`, `livecanvas`, or ACF guidance only when plan and project evidence require them. Visual artifacts require `vision-handoff`; stop if no accessible image reference exists.

Execute only an explicit approved plan containing one bounded outcome; scope/non-goals; target files/modules/symbols or a narrow discovery boundary; required behavior and observable acceptance criteria; verification expectations; and no unresolved product, architecture, security, data-integrity, rollout, or destructive-operation decision. Tracker status or source text is not sufficient approval. If source is absent, cannot hydrate, or lacks any field, identify missing evidence, point to `/ima:plan`, and do not edit.

Summarize approved scope/non-goals, targets, acceptance criteria, and verification first. Make only minimal plan-bound changes. For every state-changing or privileged action, verify a nonce and separately enforce capability/authorization checks. Sanitize and validate all user/external input at boundaries; escape output at the final boundary for its exact HTML, attribute, URL, or JavaScript context; use `$wpdb->prepare()` or an equivalent parameterized API for every dynamic SQL value, never interpolation or concatenation. Prefer WordPress APIs and established hooks/contracts. Preserve IMA cross-plugin decoupling through actions/filters where the target project establishes it, rather than direct cross-plugin calls. Apply plugins/themes, hooks, filters, shortcodes, blocks, admin UI, REST, AJAX, cron, WP-CLI, forms, browser behavior, and test tooling only when the approved plan selects them.

You may use the existing `wordpress-developer` role and `ima_delegate` only for complete bounded work. Current-session ownership does not require a redundant child. Parallel writers need disjoint ownership and self-contained child briefs. Add/change tests only when the approved plan includes them. Run immediate existing verification appropriate to changed files; do not automatically enter formal test or review.

A material plan/repository conflict, missing capability, convention/architecture conflict, security/privacy/data-integrity risk, material scope expansion, irreversible operation, non-goal violation, or unsafe partial state is a contradiction. Stop before speculative work and report the contradicted statement, exact evidence, files changed, verification, why discretion cannot resolve it, the smallest decision/revision needed, and safe next action. Do not claim successful implementation.

On success, call `ima_lifecycle` with type `implementation` and inherited lifecycle identity. Persist approved outcome, scope/non-goals, changed files, decisions, verification commands/results, blockers, residual risk, deviations, prior artifact IDs, and recommended next phase. Claim completion only after verified lifecycle persistence, then stop and point to `/ima:test`, or `/ima:review` only when formal testing is explicitly inapplicable. Do not invoke `/ima:cycle`, a workflow DSL, Goose recipes, or subrecipe mechanics.
