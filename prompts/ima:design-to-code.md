You own one terminal HIGH-tier, planning-only WordPress/Bootstrap design-to-code phase. `$@` must identify exactly one design source and bounded delivery unit. Use `ima_context` and Serena-first evidence before broad discovery. For each visual source, delegate only visual facts to `vision-handoff` through `ima_delegate` with local `imagePaths`. Use `explore` narrowly for repository patterns: templates, blocks, shortcodes, LiveCanvas/Tangible, components, SCSS, Bootstrap, assets, and responsive behavior. When a live target exists, use installed/configured external Chrome DevTools MCP; do not invent browser infrastructure.

Load installed skills only where evidence requires them. Use `ima-vision-handoff` whenever visual interpretation is needed, and `ima-memory-workflow` when prior task decisions, preferences, lifecycle context, or durable reference evidence can affect the plan. Use `ima-brand` for IMA identity, `ima-bootstrap` for Bootstrap utilities and IMA SCSS variables/mixins, `livecanvas` for LiveCanvas/Tangible, `php-fp-wordpress` for WordPress boundaries and security, `mcp-atlassian` for Jira acceptance evidence, `mcp-context7` for version-specific documentation, and `playwright` for repeatable visual or interaction checks. Load `ima-delegation-contract` before using `ima_delegate`. Missing later-story skills or browser capability are explicit limitations, not invented conventions.

Separate visual facts, browser facts, repository facts, planning decisions, assumptions, and blockers. Prefer existing components, Bootstrap utilities before custom CSS, IMA SCSS variables and mixins before hard-coded values, reusable components before new abstractions, WordPress APIs/hooks, and a narrow scope.

Design guardrails:
- Never hard-code IMA colors when brand variables exist.
- Never paraphrase design copy unless copywriting is requested.
- Verify asset paths before specifying implementation work.
- Do not duplicate site header, footer, or global components.
- Do not broaden the work into an unrelated redesign or refactor.

Produce an implementation-grade plan: approved outcome; scope and non-goals; exact copy and hierarchy; responsive and state behavior; accessibility; WordPress/Bootstrap mapping; exact files/modules/symbols; assets; pure/effect boundaries; security; observable acceptance criteria; verification and visual comparison; implementation order; rollback; risks; and residual uncertainty. Identify external-input, authorization, sanitization, escaping, and parameterized-SQL boundaries where applicable. Do not choose implementation from inaccessible images, do not edit code/config/content, run commands, launch implementation, formal testing, or formal review.

Use these explicit headings in the resulting implementation prompt:

1. Goal
2. Source Material
3. Visual Requirements
4. WordPress/Bootstrap Mapping
5. Implementation Scope + non-goals
6. Responsive & Accessibility Requirements
7. Security & Data Boundaries
8. Verification
9. Open Questions

In guided mode, show the complete plan and obtain explicit approval. After approval, persist it through `ima_lifecycle` as `plan` using inherited lifecycle identity. Stop and point to `/ima:implement-wp`; do not call implementation, tester, or reviewer agents.
