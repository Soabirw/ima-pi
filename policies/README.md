# IMA policies

FNR-3014 keeps delegation policy small and explicit. Agent tiers resolve through configured `HIGH`, `MID`, `LOW`, and `vision` roles; optional `reviewVerify` routes fresh second opinions or visibly falls back to fresh `HIGH`. Missing or incompatible minimum capability fails closed: HIGH and vision never silently downgrade or substitute. A child may receive only its definition's tools and authority.

A delegation request contains one to four complete assignments. Read roles cannot claim write scope; writing roles require repository-relative ownership; traversal, absolute paths, symlink escapes, duplicate IDs, and overlapping concurrent scopes are rejected before spawning. Writing children receive mechanically scoped `write`, `edit`, and deliberately narrow `bash` tools with realpath/symlink-safe ownership checks and fail-closed redirect classification. Every child gets a self-contained brief and cannot delegate further.

Only one retry is allowed, and only for a transient provider failure or a materially improved brief. Uncertain partial writes, unavailable/authenticated models, plan contradictions, and architecture, security, scope, or data-integrity decisions are narrow structured escalations, not broad model or phase promotion.

The same high-confidence mechanical mutation boundary is visible during production delegation as a sanitized safety interception; raw command text, arguments, paths, output, and provider payloads are not activity data. Cancellation emits a cancelling state before child abort, preserves work that already succeeded, and reports each cancelled writer's declared scope only as a possible partial effect. Cancellation never implies rollback: inspect `git status --short` and diffs limited to the reported scopes before rerunning. No permission matrix, per-command confirmation, telemetry log, or broader destructive-action classifier was added.

Initial review and each Critical/Warning verifier second opinion are always fresh. Reviewer and verifier roles are product-read-only; unverified Critical/Warning candidates cannot become actionable. Documenter writes are mechanically restricted to exact Markdown/text documentation targets, and external persistence remains parent-owned. Reviewer reuse is limited to rereview or verified finding follow-up; implementation reuse is limited to implementation follow-up or review resolution; vision reuse remains within one visual thread. Session records retain only sanitized identity and status metadata. This is not a policy engine, workflow DSL, permission matrix, or telemetry system.
