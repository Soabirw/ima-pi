## Command surface

```text
/ima:cycle start [--review-cap 0-10] [--implementation generic|js|wp] <source>
/ima:cycle status
/ima:cycle stop [--ack]
/ima:cycle resume
/ima:cycle close [--commit-prep]
```

Accepted sources are one Jira key or supported Jira browse URL, or one exact `taskwarrior <project> <uuid>` pair. A Story is the lifecycle unit; checklists do not create independent cycles.

New cycles default to `generic`. Explicit `generic`, `js`, and `wp` modes select `/ima:implement`, `/ima:implement-js`, and `/ima:implement-wp` respectively; all use the configured `implement` route. The selected mode persists in cycle state. Legacy schema-v1 state without a mode normalizes to `js`; an explicitly present invalid mode is rejected.

## Fixed lifecycle and user gates

`/ima:cycle` coordinates only this fixed lifecycle:

```text
plan -> implement -> test -> review -> resolution/rereview when requested -> document -> close
```

It is not a generic workflow engine or configurable graph. Starting deliberately dispatches `plan`; after accepted phase evidence, the coordinator waits for explicit `resume` rather than progressing automatically. `status` only reports state. `stop` pauses the active cycle and requests Pi abort; `--ack` is required when stopping a write-capable phase. `resume` explicitly dispatches the current allowed phase. When a phase persisted an explicit `BLOCKED` outcome and its external blocker is later corrected, `resume` may retry that same phase while preserving the blocked evidence. Review-cap, defect, invalid-transition, and post-tracker-close blocks remain terminal and cannot be bypassed by `resume`.

A review `REQUEST_CHANGES` enters `resolution` only within the configured cap, `RESOLVED` enters `rereview`, and review/rereview approval enters `document`. A document `READY` outcome makes the cycle closeout-ready; it never closes a tracker by itself. Normal `close` requires TUI confirmation and mutates exactly the selected source tracker. `close --commit-prep` performs only read-only Git status and diff checks.

## Safety, persistence, and Phase 1 durability

For every phase, including `document`, configured phase routing occurs before prompt expansion/injection. Lifecycle evidence is accepted only when project, lifecycle, source, expected phase, receipt, and semantic recall all match and the submitted artifact contains exactly one canonical outcome marker.

Phase 1 stores cycle intent/configuration and the last-known phase in project-local `.ima-cycle/active.json`. The folder creates its own `.ima-cycle/.gitignore` containing `*`, never changes the repository-root `.gitignore`, and stores no credentials. `active.json` is a validated cache; verified Vestige lifecycle artifacts remain the authoritative phase truth.

A provisional `awaiting-evidence` snapshot persists before prompt expansion or injection. Prompt expansion, asynchronous send, handshake verification, and handshake timeout failures are advisory after that write; only a synchronous prompt-injection throw is a hard error. Buffered advanced evidence is discarded on a failed handshake, leaving the provisional snapshot for reconcile-first recovery.

On `session_start`, `status`, and `resume`, active state reconciles verified lifecycle artifacts before reporting or dispatching. A missing or corrupt cache falls back safely to the branch cache or a fresh source-derived lifecycle key. A stale cache is corrected by verified lifecycle evidence, so `/ima:new` and a fresh terminal do not create a no-cycle-running ghost.

### Root-cause mapping and deferrals

- RC1: persist-before-handshake prevents a prompt dispatch from orphaning cycle state.
- RC2: `.ima-cycle/active.json` restores cross-session intent; reconciliation corrects it from Vestige.
- RC3: implementation, test, review, resolution, and rereview prompts recall the latest verified lifecycle artifact by canonical lifecycle key when no resume packet is present.
- Autonomous tail, autonomous planning, concurrent cycles, new store types, and a standalone CLI remain deferred to Phases 2 and 3.

Before close, closeout evidence is revalidated. The coordinator performs one confirmed tracker mutation, then persists lifecycle closeout evidence. Those external writes cannot be atomic: if tracker mutation succeeds but lifecycle persistence fails, the state is `blocked-after-tracker-close` and the tracker mutation is never retried automatically.
