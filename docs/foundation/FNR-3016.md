# FNR-3016 — IMA Gateway-Service Integration

## Scope and current approved outcome

FNR-3016 introduced the narrow model-callable integration boundary: `ima_context` assembles project context and `ima_lifecycle` persists complete lifecycle evidence through the selected lifecycle authority. Serena, Vestige, Jira, Taskwarrior, Plane, BookStack, and Qdrant remain external boundaries; the package does not expose their SDKs or create a workflow engine.

The current Serena-session hardening is approved under `plane:ima:SKYNET-238`. Its evidence includes an approved plan, two implementation records, two resolution records, and final approval. Those ordinary source/artifact identifiers are **non-secret evidence values**. They are not private session state, configuration, credentials, or authorization. This document records the implemented contract, not live-service acceptance or tracker closure.

## Architecture and contracts

- `lib/ima-context.ts` is the pure schema-version-1 source-validation, source-normalization, Serena-state evaluation, context-derivation, and sanitization core.
- `lib/serena-mcp-session.ts` is the strict same-connection Serena capability/session boundary. It discovers supported tools, validates only the accepted schema semantics, prepares private session state when required, and never projects that state.
- `lib/serena-lifecycle-client.ts` applies the prepared Serena session to exact activation, listing, read, and single-write/direct-read-back lifecycle operations.
- `extensions/integrations.ts` is the thin Pi shell. It owns injected process/filesystem effects, package-owned direct MCP session boundaries, context/lifecycle registration, and provider-native routing; it does not reconnect or fall back to bypass a Serena failure.

`ima_context` accepts exactly one Jira key, Taskwarrior project + UUID, typed Plane work item, root-contained regular file, Vestige memory ID, lifecycle key, canonical manual-phase reference, or bounded free text. It preserves optional durable-knowledge lookup through package-native Qdrant/Ollama access. It returns one versioned `PhaseContext` with source content/references, explicit Serena memory state, bounded durable references, and sanitized diagnostics.

`ima_lifecycle` follows the four-provider selection and checkout-local pin contract. The selected provider owns immutable persistence and exact verification; Serena is used only when it is the selected or pinned provider. This contract does not create a pin, select a provider, migrate evidence, mix providers, or close a tracker.

## Serena bootstrap and session boundary

The package discovers Serena tools and invokes accepted calls on one MCP connection. It accepts only exact supported input schemas for activation, instructions, memory listing, memory read, and memory write; advertised optional list/write fields are not used. Unknown fields, unsupported schema semantics, duplicate tool declarations, inconsistent session requirements, or ambiguous session-field names fail before a Serena call.

If the advertised non-instruction tools require a private session field, every such tool must require the same supported field. The package loads `initial_instructions` before activation, listing, reads, or writes. Initialization and instruction-response carriers are independently validated and every present carrier must agree. JSON-shaped text is validated as JSON before it can be treated as opaque text. SDK-normalized empty content is accepted only with a valid structured session carrier. No session value appears in a `PhaseContext`, lifecycle result, diagnostic, delegated-child result, or other public projection.

A caller predating capability discovery retains a compatibility path with the historical unparameterized order: exact activation, instructions, listing, then reads. The normal package MCP path uses discovery. Both modes require the exact existing-checkout activation receipt; created-project receipts, generic text, or mismatched checkout identity block before dependent memory effects.

The context bootstrap reads every listed member of this standard set:

1. `core`
2. `conventions`
3. `tech_stack`
4. `suggested_commands`
5. `task_completion`
6. `memory_maintenance`

Missing standard memories remain explicit degraded context and are never written. A discovery, session, instruction, activation, listing, or read failure returns bounded sanitized diagnostics with no reconnect, fallback, or effectful retry.

## Serena lifecycle boundary

The Serena lifecycle client first validates checkout-local Serena project/layout prerequisites, prepares the same MCP session, and then verifies exact checkout activation. It treats both `memories` and `read_only_memories` as listing evidence. The provider persists an immutable deterministic memory at most once and accepts `stored` only after direct exact read-back verification. Existing identical evidence is `unchanged`; conflict, malformed evidence, uncertain dispatch, cancellation, failed verification, or incomplete recall blocks. `get` and `reconcile` are always read-only, and recall returns no authoritative partial result.

A dispatched but unsettled write retains a local-only cooperative exclusion. It is never retried, expired, stolen, deleted, or used to justify provider fallback. Operator-authorized recovery is separate from exact read/reconcile evidence.

## Source boundaries and privacy

Jira hydration uses the installed Atlassian helper only; Taskwarrior uses narrow read-only export; typed Plane hydration uses the packaged Plane helper; cited Vestige retrieval uses direct MCP; free text is never reinterpreted; and files must be regular, non-binary, bounded, and root-contained after realpath resolution. Package-native Qdrant access remains bounded and does not override lifecycle authority.

The shell uses argument arrays, fixed output/process limits, untrusted-JSON parsing, injected dependencies, and bounded result mapping. It does not return raw upstream payloads, stderr, credentials, authorization headers, environment dumps, private session data, or full transcripts. Invalid prepared calls use static/sanitized outcomes; source exceptions collapse to safe boundary codes.

## Configuration classification

- Serena MCP and any configured lifecycle service destination are **platform bindings**.
- Serena project paths, `~/.serena` configuration, project `.serena` layout/memories, checkout-local pins, private session state, leases, and retained local output are **local-only values**.
- Serena/MCP/provider credentials and tokens are **secrets** and must remain outside Git, ordinary variables, fixtures, docs, logs, and lifecycle artifacts.
- Ordinary source identifiers, artifact IDs, and provider preferences are **non-secret variables/evidence values**.

## Automated verification and limits

Recorded provider-free coverage includes closed context schemas, source boundaries, same-connection discovery, instructions-first private bootstrap, carrier agreement, JSON-first parsing, structured-only SDK normalization, pre-effect schema refusal, exact activation in both modes, six-memory hydration, lifecycle one-write/direct-read-back, exact read/reconcile, bounded recall, cancellation, and uncertain-write retention. No live Serena/MCP/provider acceptance, production write, routing rollout, provider migration, or tracker closeout is claimed. Synthetic tests cannot establish live transport timing, real service protocol behavior, configuration availability, or resistance to privileged external mutation. ## Rollback and human gate

This is additive contract hardening. Any rollback must be separately reviewed against provider-pin authority, immutable evidence, and compatibility behavior; it must not repair, repin, migrate, delete local Serena state, or retry an uncertain write. The next gate is a separately authorized human live-service acceptance decision, not an automatic test or tracker action.
