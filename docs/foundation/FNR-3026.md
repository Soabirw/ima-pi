# FNR-3026 — Pi-native release preparation

## Outcome

FNR-3026 ports the IMA `goose-ship-it` outcome as the Pi-native `/ima:ship-it` prompt and reusable `ima-git` skill. It prepares a staging `release/*` branch or an immutable production `v*` tag, verifies the pushed remote ref with the matching project dry-run, and leaves actual deployment under human authority.

| Source outcome | Pi-native resource | Boundary |
| --- | --- | --- |
| release-preparation recipe | `/ima:ship-it stg|prod [project-path] [release details]` | natural-language, terminal operational prompt |
| IMA Git policy skill | `ima-git` | reusable trunk/release/tag and preflight policy |

## Pi rationale and authority

Markdown prompt plus skill is sufficient because Git and npm already supply the effects. No extension, parser, dependency, deploy adapter, workflow engine, or Goose mechanics were introduced. The prompt intentionally repeats critical authority constraints: it may change a checkout, fetch, create/fast-forward/push the selected release ref, and dry-run; it never deploys, commits, stashes, cleans, force-pushes, rewrites history, or moves/deletes tags.

## Release contracts

Readiness requires a resolved Git root, `origin`, a fully clean worktree, `git fetch origin --tags --prune`, a `package.json` `ship-it` script, and optional `.ima-ship-it.json` inspection. Its absence is permitted. The project dry-run remains authoritative, with latest JSONL deploy/ship-it log evidence checked when available and conflicts treated as failures.

Staging updates only a `release/*` branch that can fast-forward from current `main`, verifies its remote SHA, leaves it checked out, then always runs `npm run ship-it -- stg --dry-run`. A failure preserves the pushed branch and routes fixes through `main`.

Production selects a pushed `release/*` source, captures its HEAD as the release commit, and creates only a new annotated unused `v*` tag. It verifies both the direct remote tag object and the remote peeled `^{}` target, requiring that target to equal the captured release commit before detaching at the tag and running `npm run ship-it -- prod --dry-run`. Failed production preflight preserves the immutable tag; later fixes require normal trunk/release flow and a new incremented tag. Only successful preflight permits reporting the exact non-dry-run command; it is never executed.

## Verification and limitations

Provider-free tests assert prompt/skill contracts and Pi package discovery/provenance. `npm test` and `git diff --check` validate the repository change. They do not prove model adherence, Git-host behavior, a real project ship-it implementation, or deployment behavior.

Manual acceptance must use a disposable or explicitly approved non-production Git fixture with `origin` and a stubbed `ship-it` script. Exercise dirty-tree blocking, new/existing/divergent staging state, staging dry-run with no deployment, annotated production tagging and detached checkout, existing-tag refusal, failed production dry-run preservation, successful exact next-command reporting, and ambiguous production branch clarification. Never target a real deploy.
